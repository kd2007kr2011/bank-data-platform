# 零售银行数据平台：项目需求说明书

## 1. 项目概述

### 1.1 项目背景

零售银行在日常经营中会产生大量与客户、账户、交易、贷款和还款相关的业务数据。为了支持日常经营分析，通常需要对不同业务数据进行整合、清洗、统计和汇总，为客户分析、交易监控和贷款管理等场景提供数据支持。

本项目通过模拟零售银行的核心业务流程，构建一个轻量级的数据处理与分析平台，实践关系型数据库设计、SQL 开发、数据处理、数据质量检查及业务指标分析等技术。

### 1.2 项目目标

1. 建立客户、账户、交易、贷款和还款等基础业务数据模型。
2. 使用 MySQL 存储和管理业务数据，通过 SQL 完成数据查询、关联和统计。
3. 使用 Python 生成合成数据，并实现基础数据处理与质量检查。
4. 构建统一的业务指标统计口径，支持后续报表和可视化分析。
5. 形成结构清晰、可复现、便于维护的工程项目。

### 1.3 项目边界

**本期建设范围：**

- 客户基本信息及客户状态管理。
- 客户与账户之间的关联查询。
- 交易记录查询及交易金额、交易笔数统计。
- 贷款合同、放款记录和还款记录管理。
- 客户数、账户数、交易笔数、交易金额和贷款余额等指标统计。
- 基础数据质量检查与项目运行说明。

**本期暂不建设：**

- 真实银行系统的接口接入。
- 真实客户身份认证、支付和贷款审批功能。
- 生产级实时数据处理与高可用部署。
- 复杂的信用评分、反欺诈和风险预测模型。

本项目定位为个人学习与工程实践项目，不替代真实银行核心业务系统。

## 2. 业务需求

### BR-01：客户信息查询

系统应支持客户基本信息的存储与查询，包括客户编号、客户名称或合成标识、客户类型、客户状态及开户日期等字段。

- 数据对象：`customers`
- 主要用途：查询客户总量、客户状态分布及客户基础信息。
- 验收标准：能够根据客户编号查询唯一客户记录，并按客户状态进行分类统计。

### BR-02：账户信息查询

系统应支持账户信息管理，并能够查询账户所属客户、账户类型、账户状态及开户日期。

- 数据对象：`accounts`
- 主要用途：分析客户持有账户的情况，统计账户总数及账户状态分布。
- 验收标准：能够根据客户编号查询其关联账户；账户关联的客户必须存在；能够正确区分客户数与账户数。

### BR-03：交易记录统计

系统应支持按照交易日期、交易类型、交易状态和账户编号查询交易记录，并统计指定期间的交易笔数和交易金额。

- 数据对象：`transactions`
- 主要用途：分析交易规模、交易类型分布及每日交易情况。
- 验收标准：能够按日期和交易类型进行分组统计；统计时区分成功、失败、撤销和冲正等状态，避免将无效交易直接计入有效交易指标。

### BR-04：贷款与放款记录查询

系统应支持查询贷款合同基本信息，包括贷款编号、客户编号、合同金额、贷款状态、放款日期等，并记录贷款实际放款情况。

- 数据对象：`loans`、`loan_disbursements`
- 主要用途：分析贷款客户数量、合同规模和放款规模。
- 验收标准：能够根据客户编号查询关联贷款；能够区分贷款合同金额与实际放款金额；放款记录必须关联有效的贷款合同。

### BR-05：还款记录与贷款余额统计

系统应支持查询贷款还款记录，并按照指定日期统计还款金额和未偿还本金余额。

- 数据对象：`loan_repayments`、贷款及放款记录
- 主要用途：分析贷款偿还情况、还款规模和剩余本金。
- 验收标准：能够按日期统计有效还款记录；能够根据放款本金和已确认的本金偿还记录计算贷款剩余本金，并区分本金偿还与利息支付。

注：本期可暂不考虑复杂的计息、罚息、展期和核销规则，贷款余额计算以文档中明确的简化业务规则为准。

## 3. 非功能需求

### NFR-01：数据质量

- 客户编号、账户编号、交易编号和贷款编号等关键标识应满足唯一性要求。
- 必填字段不得为空。
- 账户、交易、贷款及还款记录应满足相应的关联完整性要求。
- 金额字段不得出现不符合业务规则的数值。
- 应提供基础数据质量检查 SQL 或 Python 脚本。

**验收标准：** 能够执行重复记录、缺失值、无效关联及异常金额检查，并输出检查结果。

### NFR-02：数据安全与隐私

- 所有业务数据均使用程序生成的合成数据。
- 不使用真实客户姓名、身份证号、银行卡号、账户流水或其他真实银行业务数据。
- README 和数据说明中应明确声明数据来源及项目的模拟性质。

**验收标准：** 项目数据和文档均明确标识合成数据，不包含有意导入的真实客户隐私信息。

### NFR-03：数据处理可追溯性

- 数据生成、导入和统计过程应具有清晰的执行顺序。
- 关键处理任务应记录执行结果及异常信息。
- 指标定义和计算规则应有文档说明。

**验收标准：** 能够根据项目文档定位数据生成、数据导入、质量检查及指标统计所对应的脚本或 SQL 文件。

### NFR-04：可复现性与可维护性

- 提供清晰的目录结构和环境配置说明。
- 数据库建表、合成数据生成和基础统计应能够按照文档重新执行。
- SQL、Python 脚本及文档应按功能分类存放。
- 代码和配置中不得包含真实账号、密码或其他敏感凭据。

**验收标准：** 在满足环境依赖的前提下，按照 README 的步骤能够重新建立数据库、生成合成数据并执行基础统计。

## 4. 核心业务指标定义

为避免同一个指标出现不同统计结果，本项目统一采用以下初始口径。

| 指标 | 指标定义 | 主要数据来源 | 统计方式 |
|---|---|---|---|
| 客户数 | 指定统计时点符合条件的去重客户数量 | `customers` | 按客户编号去重，并依据客户状态及统计时点筛选 |
| 账户数 | 指定统计时点符合条件的去重账户数量 | `accounts` | 按账户编号去重，并依据账户状态及统计时点筛选 |
| 交易笔数 | 指定期间内成功完成且未被撤销或冲正的有效交易数量 | `transactions` | 按交易编号去重，结合交易状态及业务规则筛选 |
| 交易金额 | 指定期间内有效交易的金额汇总 | `transactions` | 汇总符合口径的交易金额；流入和流出分开统计 |
| 放款金额 | 指定期间内实际完成的贷款放款金额 | `loan_disbursements` | 汇总有效放款记录，不直接使用贷款合同金额替代 |
| 还款金额 | 指定期间内实际完成的贷款还款金额 | `loan_repayments` | 根据还款状态及还款类型汇总，必要时分别统计本金与利息 |
| 贷款余额 | 指定统计时点尚未偿还的贷款本金 | 贷款、放款及本金还款记录 | 累计有效放款本金减去截至该时点的有效本金偿还额 |

### 4.1 统计口径说明

1. 客户数与账户数是不同的指标。一个客户可以拥有多个账户，因此不能用账户记录数代替客户数。
2. 交易笔数是交易事件的统计，不等于所有交易表记录的行数。失败、撤销及冲正记录需要按照明确的业务规则处理。
3. 放款金额与贷款合同金额不同。合同金额表示合同约定的额度或金额，放款金额表示实际完成的资金发放。
4. 贷款余额属于时点指标，放款金额和还款金额通常属于期间指标，两者不能混用。
5. 本期贷款余额暂不考虑利息计提、罚息、核销等复杂因素，并假设已确认的本金偿还记录能够准确反映本金减少额。
6. 如需统计历史时点的客户数、账户数或贷款余额，应使用能够还原历史状态的数据，不能直接使用当前状态代替历史状态。

## 5. 数据模型初步规划

| 逻辑表名 | 主要内容 | 关键关联 |
|---|---|---|
| `customers` | 客户基本信息 | 客户主键 |
| `accounts` | 账户基本信息 | 关联客户 |
| `transactions` | 账户交易事件 | 关联账户 |
| `loans` | 贷款合同信息 | 关联客户 |
| `loan_disbursements` | 贷款实际放款事件 | 关联贷款合同 |
| `loan_repayments` | 贷款还款事件 | 关联贷款合同 |

以上为逻辑数据模型。具体字段、主外键、状态枚举及金额计算规则将在数据库设计阶段进一步确定。贷款余额可先通过 SQL 查询计算，后续再根据需求决定是否建立汇总表。
